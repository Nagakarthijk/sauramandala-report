# Dhubri Pilot — Last-Mile Maternal Emergency Response System

**Status:** Concept / Discovery — pre-build
**Repository:** nagakarthijk/sauramandala-report
**Location:** This is a separate project from the Doorstep Incubation Protocol (`/PROTOCOL.md`, root `.html` files). It lives entirely inside this `dhubri-pilot/` folder so the two don't get tangled.

## What this is

A coordination layer for high-risk pregnancy (HRP) and maternal emergencies on the river chars (unconnected river islands) of Dhubri, Assam — where the nearest health facility is only reachable by boat. Today, when an emergency happens, a frontline health worker (ASHA/Anganwadi/ANM) or family scrambles informally to find a boatman, and the receiving facility has no warning and no patient details when the boat arrives. This project builds the digital coordination layer — on top of Glific (WhatsApp-based conversational platform) — to replace that ad-hoc scramble with a triggered, tracked, multi-party flow: **frontline worker → boatman directory → facility → 108/CNES ambulance boat → dashboard.**

Type-checks cleanly; not yet deployed or run against a real account.
- [`dhubri-data.js`](./dhubri-data.js) + [`dashboard.html`](./dashboard.html) — a demo case-tracker dashboard prototype with placeholder sample data (open `dashboard.html` in a browser to walk through it — nothing in it is real).
- [`simulator-scenarios.json`](./simulator-scenarios.json) + [`simulator.html`](./simulator.html) — a scripted WhatsApp/SMS/IVR chat simulator for demoing the design to someone without any of the real infrastructure: pick one of 5 scenarios (happy path, family report confirmed, family report timed out, boatman pool escalates to 108/CNES, full omnichannel accept) and step or play through simulated phone windows for every actor plus a live control-room dashboard panel. Pure front-end, no backend — open `simulator.html` directly in a browser. **Still pre-blueprint** — doesn't yet reflect the BRC/dual-checklist/single-button mechanics.
- [`whatsapp-journey.json`](./whatsapp-journey.json) + [`whatsapp-journey.html`](./whatsapp-journey.html) — **eight** complete case-to-facility journeys using real WhatsApp Cloud API / Gupshup message JSON shapes, every message's exact payload inspectable via a "raw WhatsApp JSON" toggle. SCN-01–07 cover day/night/family-report/escalation/flooding/fuel-shortage scenarios (pre-blueprint mechanics). **SCN-08 is the fully-reconciled flagship** — single-button RED trigger, 5-way parallel fan-out (boat pool + facility + BRC + 108 Coordinator), a bare SMS `*` accept from a feature-phone boatman, two separate readiness checklists, dual ambulance ETA shared with three parties, and the closing reflection message. This is the one to show the team. Open `whatsapp-journey.html` and pick SCN-08.
- [`game/`](./game/) — **live multiplayer training exercise**: real people play the actual roles (worker, 2 boatmen, facility) on their own phones in the same room, peer-to-peer, no server. Their real decisions and reaction speed drive a live scenario with day/night, flooding, and fuel-shortage modifiers, and the outcome is a genuine stake — Safe Delivery, a complication, or a death — based on how fast the team coordinates. The scenario/outcome engine is thoroughly unit-tested (`node game/game-engine.test.js`, 59 assertions); the real device-to-device networking has **not** been live-tested (this sandbox's network policy blocks the PeerJS CDN/broker outright — do a quick two-device test yourself before running a group session). See `game/README.md`. **Still pre-blueprint.**
- [`glific-flows/`](./glific-flows/) — **real Glific-native flow JSON, rebuilt from scratch against the team's own detailed walkthrough of the actual process** (frontline worker → severity/location/patient capture → boatmen + facility broadcast → boatman accept → worker-driven status updates → facility prepared). Three flows: `FLOW-EMERGENCY-REPORT.json`, `FLOW-BOATMAN-ACCEPT.json`, `FLOW-STATUS-UPDATE.json`, plus `char-config.js` (the per-char Group/Contact routing) and `REGISTRY_SHEET_DESIGN.md` (the Google Sheet registry design, and why Glific can't just read it live to decide who to message). Start with `glific-flows/README.md`.

**⚠ Not yet reconciled against the rest of this folder.** This newest pass describes the process directly from the team, without reference to the Block Referral Coordinator / 108 parallel-dispatch / dual-ETA / two-checklist mechanics that `SERVICE_BLUEPRINT.md`, `FLOWS.md`, `SOP.md`, `schema.sql`, and `backend/` are all built around. It's not yet clear whether this is a simpler subset of the same process, a different (possibly more accurate) description superseding parts of the blueprint, or something that needs both to be true at once — that needs a real answer from the team before the two are merged. Until then, treat `glific-flows/` as the current, most-detailed source for the worker→boatman→facility mechanics specifically, and the other docs as the source for BRC/108/dual-ETA/facility-checklist mechanics, which `glific-flows/` doesn't yet implement.
